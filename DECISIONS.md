# Decisions

## ADR-001: DPF built-in WebView, not dpfwebui
DPF @ 4238e1c7 (2025-10-23) has `UI_TYPE=webview` (WKWebView on macOS). dpfwebui was last updated 2024-05 and is tied to an older DPF.

## ADR-002: Integer tick timing
PPQ = 3840 per quarter; all resolutions (incl. triplets) are exact integers. No float-seconds accumulation.

## ADR-003: Bridge transport
JS→C++: DPF-injected `setState('cmd', json)`; arrives on the main thread via `Plugin::setState` (undeclared keys are not rejected on that path).
C++→JS: `PulsUI::uiIdle` drains a main-thread outbox (reached through `getPluginInstancePointer()`), then calls `UI::stateChanged('evt', base64(json))`
(DPF does not escape the string it injects into JS, hence base64). Playhead telemetry uses atomics read in `uiIdle`.

## ADR-004: Resources location
macOS CLAP: `puls.clap/Contents/Resources/index.html` (DPF `getResourcePath`); Linux/Windows: `puls.clap/resources/`. The DPF WebMeters example uses `resources/` and would not resolve on macOS.

## ADR-005: Host quarter position
DPF's CLAP adapter derives bbt from `song_pos_beats` (quarters). Absolute quarter pos = (bar-1)*beatsPerBar + (beat-1) + tick/ticksPerBeat; only valid when `bbt.valid`.

## ADR-006: RT handoff is a wait-free triple buffer of whole snapshots
`engine/SnapshotExchange.hpp`. The main thread copies the Model into `EngineSnapshot` (pattern + settings, ~7.5 KB POD) and publishes; `run()` acquires once per block. No allocation, locks or deletes on the audio thread; tested with a producer thread for tearing/ordering. Sounding-note bookkeeping lives in `Sequencer`, so replacing the pattern mid-note never leaves stuck notes.

## ADR-007: nlohmann/json 3.11.3 for non-RT code only
Vendored single header (`third_party/`, sha256 in its README), used by `state/` and `bridge/`, never by `engine/` or `run()`. Plugin builds with `-fno-fast-math`: DPF's default `-ffast-math` removes `isfinite` guards in the engine and breaks json.hpp's infinity handling, and the tests are built without it.

## ADR-008: Bridge validation is atomic and strict
Commands/props are applied to a copy and committed only if every present key is valid; invalid commands yield an `error` event and change nothing (the UI then re-requests `init`). Persisted state is stricter still: any invalid value rejects the whole state, the model keeps its previous value and an `error` event is queued. Steps are serialized sparsely (defaults omitted). Tracks are addressed by stable id, never index.

## ADR-009: Phase 2 scope vs. the plan
the pattern bank and `selectPattern` were deferred to Phase 4 (done, ADR-011); undo/redo was pulled forward (ADR-010) (there is exactly one pattern now; the toolbar shows its name). Velocity drag is coalesced to one command per animation frame plus the final value. `settings` is an added event. Toolbar resolution/swing act on the selected track; "−" removes the selected track.

## ADR-010: Undo/redo is snapshot-based, pattern-only, coalesced by gesture id
`model/UndoStack.hpp` keeps up to 100 whole-`Pattern` snapshots (main thread, heap, ~7.5 KB each); the Bridge copies the pattern before each command and records it if the command changed anything (`setSettings` excluded: enabled/anchor are not undoable). `undo`/`redo` answer with `patternChanged` + `history {canUndo, canRedo}` (also in `init`). `setStepVelocity` may carry a non-zero `gesture` id; consecutive commands with the same id/track/step keep only the first "before" state, so one drag = one undo step. History is not persisted and is cleared when state is restored. Track ids are never reused, so undoing a removal brings the same id back. Ctrl/Cmd+Z, Shift+Ctrl/Cmd+Z and Ctrl+Y work only while the WebView has keyboard focus (unverified in Bitwig).

## ADR-011: Pattern bank, selected vs playing, quantized switching
The Model holds 16 patterns; `selected` is the one viewed/edited, the *playing* one lives on the audio thread (`PatternSwitcher`) and comes back through telemetry (`playheads.pattern`), so the UI can show a queued switch. Every snapshot carries the whole bank (~120 KB memcpy per edit on the main thread); `selectPattern` goes through a wait-free `SpscQueue<SwitchRequest,16>`. The switcher resolves a request into an absolute target in musical units (next beat = next whole quarter, next bar = next multiple of the host's beats-per-bar; a block starting exactly on the boundary switches at once) and the Sequencer applies it per event: events with time >= target come from the new pattern, so the result is identical for any block size (tested 1..4096). The step grid is NOT re-anchored on a switch (tracks keep their phase, like a pattern that had always been there). Stopped or disabled: immediate. A stale target (transport jumped back) is re-resolved; selecting the playing pattern again cancels a pending switch. Default: bar while playing (setting `patternSwitch`: bar/beat/now; Alt+click = now). Undo restores the pattern the entry belongs to and shows it, but does not switch playback. Playheads are hidden while a non-playing pattern is viewed. Time-signature changes mid-song are not tracked (the signature of the current block is used).

## ADR-012: Schema v2 (whole bank) with v1 migration
`{"schemaVersion":2,"selected":n,"patterns":[<=16 patterns],"settings":{...}}`; missing slots become blank default patterns. v1 (`"pattern"`) is migrated in `migrate()` into slot 0 before validation (exercised by `ClapLoadTest`, which still restores a v1 document). Loading stays strict and atomic. History, clipboard and playheads are never persisted. Track ids are unique per pattern; `nextTrackId` is the global maximum + 1.

## ADR-013: Step selection, clipboard and keyboard
Selection is a rectangle (tracks x steps) between an anchor and a cursor; Shift+click or Shift+arrows extend it. Space/Enter toggles, Delete clears, Ctrl/Cmd+C/X/V copy/cut/paste the block (UI-side clipboard, full step data) at the selection's top-left. Multi-cell edits are one atomic `editSteps` command (<=1024 cells, one undo step). Keys are handled only while the WebView has focus and never while an input/select/button is focused or a menu is open. Not verified in Bitwig.

## ADR-014: Native NanoVG UI replaces the WebView (supersedes ADR-001, ADR-003 UI side, ADR-004)
On Linux DPF's WebView runs WebKitGTK in a separate process tree, with hardware acceleration forced off (`WebViewImpl.cpp`), so every playhead repaint was a software paint in other processes competing with the host at normal priority: short, high CPU spikes while playing and none while stopped. The editor is now drawn with DGL's NanoVG (`UI_TYPE=opengl`, built-in DejaVu Sans). It reads the Model directly through `PulsPlugin::model()` (main thread: in CLAP, `UI::setState` reaches `Plugin::setState` synchronously on the UI thread, `DistrhoPluginCLAP.cpp` `setStateFromUI`) and still sends every edit as a Bridge JSON command, so validation, atomicity and undo are unchanged. The outbox is only a dirty signal (plus error messages). Telemetry is polled in `uiIdle` (~60 Hz host timer) and the window repaints only when a playhead, transport value or edit changed. Geometry/hit-testing (`gui/EditorLayout`) and command builders (`gui/Commands`) have no DGL dependency and are unit-tested (`gui_tests`). Velocity drags send at most one command per idle tick with one gesture id (one undo step). Layout is in logical px multiplied by the host scale factor. On Linux the CLAP is a single file again (no bundle/resources); the Linux resource patch for DPF is no longer applied. Measured (Linux, JACK standalone, dummy driver, 120 bpm, 8 tracks playing): the whole process uses ~1.4 % CPU, with no extra processes. Done in milestones: (1) grid, toolbar, bank, playheads, settings, remove confirmation; (2) track/step/pattern popovers incl. text fields and a fixed color palette; (3) keyboard selection and clipboard; (4) help overlay, then `ui/` is deleted.

## ADR-015: Native popovers and text fields (milestone 2 of ADR-014)
Right-click (or Ctrl+click) on a step, a track label or a pattern slot opens a popover. Fields are data (`gui/Menu`: key, type, label, range in shown units, column); values are read from the Model on every draw and each edit is a Bridge command built by `fieldCommand`, which clamps and returns nothing when there is nothing valid to send (empty or >15-byte names, paste with an empty clipboard, a target that is gone). A menu belongs to the pattern selected when it opened and closes itself if that pattern or its track goes away (`targetValid`). The track menu uses two columns so it fits the 240 px minimum height. Sliders coalesce like the velocity drag (one command per idle tick, one gesture id); wheel steps on one control share a gesture; typed values and names are one undo step. Text editing (`gui/TextEdit`) is single-line, UTF-8 aware, limited by bytes, with a numeric mode; focusing selects all. The track color picker is a fixed 16-color palette (the 8 defaults + 8). The length box in the grid can also be typed (click without dragging). Drawing helpers live in `plugin/Paint.hpp`; the popovers in `plugin/MenuView`, which shares the editor's gesture counter. Keyboard input reaches fields only while the plugin window has focus (verified in the JACK standalone on Linux, not yet in a DAW).

## ADR-016: Native step selection and block clipboard (milestone 3 of ADR-014)
Same behavior as ADR-013, now in `gui/Selection` (DGL-free, unit-tested): a rectangle between an anchor and a cursor in track-index x step coordinates. The first arrow press places the cursor on the selected track at step 1; arrows move it (clamped), Shift+arrows and Shift+click extend; the cursor's track becomes the selected track and the cursor is scrolled into view (`EditorLayout::ensureVisible`). Space/Enter toggle the block (all on -> off, otherwise on), Delete/Backspace reset it, Ctrl/Cmd+C/X/V copy, cut and paste full step data at the selection's top-left (clipped at the last track/step, the pasted area becomes the selection). Each edit is one atomic `editSteps` (16 x 64 = 1024 cells, exactly the Bridge limit) and one undo step. The selection is dropped when the pattern on screen changes and clamped when tracks disappear; the clipboard is UI-side and not persisted. Keys go to text fields first, then to an open popover, and are ignored by the grid while a toolbar popup is open. With the WebView gone, DPF's Linux resource-path patch was reverted (no resources are loaded).

## ADR-017: Native help overlay; the WebView UI is removed (milestone 4 of ADR-014)
The help is a modal overlay (toolbar ? button or the ? character; Esc, × or a click outside close it; while open, grid and global shortcuts are ignored). Its content and geometry live in `gui/Help` (DGL-free, tested); rows wrap, so their heights are measured with NanoVG while drawing and fed back to clamp the scroll (wheel, Up/Down, PageUp/PageDown). Content follows the former help, adjusted to the native gestures (typed length, menu controls). `ui/` (TypeScript, Vite, npm) is deleted together with its ignore rules and npm permissions; `docs/phase0-report.md` is kept as a historical record. The native editor has only been built and run on Linux (JACK standalone); macOS has to be rebuilt and checked before claiming it there (rule 7).

## ADR-018: Small host position errors (tempo steps, jitter, dropouts) no longer restart the grid; transport trace
Field report (Bitwig 48 kHz, 160-sample blocks, Linux, no loop): after pressing play the first pattern pass is fine, the second "slows down" (audio and playheads), later passes are regular; also with the editor closed and without CPU spikes. A `PULS_TRACE` capture showed the cause is the host, not Puls: Bitwig reported 130 bpm, ramped to 118 bpm between bar 1.87 and 1.98, stayed there until bar 2.73 and stepped back to 130 (tempo automation in the project; a CLAP plugin cannot change the host tempo). Puls followed it exactly; there were no restarts.
The trace also exposed a real weakness: `RestartOnStart` treated any block whose host position differed from the extrapolated one by more than 2 samples as a jump (notes released, grid re-anchored, i.e. the pattern restarted from step 1 mid-pass). The 118 -> 130 step inside a block moved the next block start by ~14 samples, which would have restarted the pattern; the same happened after a single block without a playing transport (DPF reports a missing `process->transport` as stopped). Now: differences up to `kResyncSeconds` (10 ms) are followed without touching the grid, the ownership window or sounding notes (`Resynced`; in the capture, exactly that block); a dropout of up to `kMaxDropoutSeconds` (250 ms) that ends where playback would have been keeps the grid (`Resumed`). Real relocations (loop wraps and seeks move by at least a step, >= 31 ms) and real stop/play still restart. Exact hosts are unaffected: output stays identical for every block size.
Diagnostics: `PULS_TRACE=<file>` (read when the plugin is created) makes run() queue one record per block (wait-free) and the editor's idle append them as CSV (host frame, block size, play state, bbt validity, position, tempo, `Sequencer::BlockKind`, events, playhead of track 1, playing pattern); the editor must be open while recording.

## ADR-019: Preview notes when steps are switched on (toggle ♪ in the toolbar)
With `settings.audition` on (default; persisted, not undoable, setting key `audition`), every step command that switches steps from off to on (`toggleStep`, `modifyStep`, `editSteps`: click, Space/Enter, paste) plays the note of each affected track once, at the velocity of its first newly active step × the track's velocity scaling (ignoring mute/solo, probability and the `enabled` switch: it answers an edit). The UI still schedules nothing (rule 4): the Bridge returns `auditions` next to its result, the plugin pushes them into a wait-free `SpscQueue<AuditionNote,64>` and `run()` plays them through `engine/Auditioner` (16 voices, fixed 200 ms length, note-on at frame 0 of the next block, sample-accurate note-off, retrigger = off+on, steal the voice closest to its end), merged by frame with the sequencer's events. It works with the transport stopped. Preview notes are not tracked by the Sequencer: a preview's note-off can end a sequenced note of the same pitch and channel that started during the preview (harmless for one-shot drums). The toolbar's pattern name shrinks from 100 to 68 px to make room (the name is also in the bank bar), so the minimum width is unchanged.

## ADR-020: Note keyboard overlay for choosing each track's MIDI note
The "MIDI note" slider in the track menu stays; a piano button next to it, and one in the toolbar (after the selected track's name, which shrinks from 90 to 58 px so the minimum width is unchanged), open a modal overlay like the help: one chip per track (two rows of 8 at most) to pick the track, an info row (hovered key, otherwise the selected track's note, with its General MIDI drum name) and a piano of whole octaves (as many as fit at >= 22 px per white key, 4 at the minimum width; ‹ › or the wheel move by an octave). A dot in each track's color marks its note on the key, the selected track first with a white ring, stacked up to what fits on the key; the selected track's key is tinted. Clicking a key sends `modifyTrack {note}`; Up/Down pick the track, Left/Right move its note by a semitone, Esc / × / a click outside close it. The overlay's track is the editor's selected track. Note names use 60 = C3 (Bitwig, Ableton, Cubase). Geometry lives in `gui/Keyboard` (DGL-free, tested).
Bridge: with `settings.audition` on, a `modifyTrack` that sets `note` previews the track's note (velocity 100 x the track's velocity scaling), also when the note is unchanged, so clicking the current key lets you hear it; this also applies to the menu slider and typed values. The note keyboard adds `"preview":true` to its `modifyTrack`, which plays the note even with ♪ off: pressing a key there is an explicit request to hear it (no double note, one command). Pressing a key animates it subtly (a little darker / lighter and 2 px shorter, with a shadow at the top): down while the mouse button is held, at least 90 ms, then easing back over 140 ms; uiIdle repaints only while that runs. A `modifyTrack` that changes nothing is no longer recorded in the undo history (and keeps the redo stack).

## ADR-021: One track per note and channel
Within a pattern no two tracks share a note on the same MIDI channel (the same note on different channels is allowed: it can reach a different instrument). The Bridge enforces it: a `modifyTrack` that changes note or channel into a pair another track uses fails atomically with an error naming that track (shown in the editor's status line, e.g. for a typed note), and `addTrack` gives new tracks the first free note from 36 up (previously 36 + track count, which could collide); explicit colliding `props` fail. Projects saved earlier that repeat a note still load unchanged and their tracks stay editable; only edits that touch note/channel are checked. `noteOwner`/`freeNote` live in `model/Model.hpp`.
In the editor: on the note keyboard a key owned by another track (on the selected track's channel) is blocked: clicking it only plays it through the new `previewNote {track, note}` command (non-undoable, changes nothing, plays even with ♪ off), the pointer shows "not allowed" and the info row says whose it is; Left/Right jump to the next free note. In the track menu the MIDI note slider snaps to the nearest free note and the wheel skips taken ones (`snapValue`).

## ADR-022: Templates (kit presets), built-in and user, per pattern
A template is a named track layout loaded into one pattern (tracks are per pattern): name, note, channel, color, length, resolution, phase and the other track props, never steps. Schema: `{"id","name","category"?,"source"?,"tracks":[track props]}`; tracks are read with the project's own `readTrackProps`, so templates and projects share one definition; 1-16 tracks, no repeated note+channel (ADR-021), `id` 1-31 of `[a-z0-9-]`. Code: `state/Templates` (no DPF; parse, `applyTemplate`, `TemplateStore`).
- Built-ins are `templates/*.json`, embedded at build time as raw string literals by `scripts/embed-templates.sh` (plugin Makefile: a prerequisite of `Templates.cpp.o`, which DPF's `$(BUILD_DIR)/%.cpp.o` pattern rule compiles; CMake: a custom command), because the Linux CLAP is a single file without resources. Adding one is adding a file. First one: `bitwig-v8-edrums-01` (Bitwig Drum Machine "v8 E-drums Kit 01", notes 36-47, channel 1, colors from the editor palette). Bitwig names notes with 60 = C3 (like Puls, ADR-020) and lays the Drum Machine's 16 pads out bottom row first: C1-D#1 (36-39) at the bottom, C2-D#2 (48-51) on top. The kit fills 36-47 (E-Kick801, E-Snare01, E-Hat801 x2 / E-Kick802, E-Clap802, v8Rimshot, E-Cymb02 / E-Tom8Hi, E-Tom8M, v8 Claves, v8 Cowbell) and leaves the top row empty. The first spec read the grid top-down (empty C2 row = 36-39, the kit on 40-51, "E-Tom3Hi"), which put every pad on the wrong note; corrected from a screenshot of the pads. Tracks are in note order, so the kicks come first.
- User templates are one `<id>.json` file each in `$XDG_CONFIG_HOME/puls/templates` (default `~/.config/...`; macOS `~/Library/Application Support/Puls/templates`, not yet built or run there). POSIX I/O on the main thread only, written atomically (temp + rename); invalid files and files whose name is not their id are skipped. Names are unique case-insensitively; built-in names and ids are reserved; the id is a slug of the name (suffixed if taken). The list is re-read whenever the dropdown opens, so templates saved by another instance appear.
- Bridge: `applyTemplate {index, template}` (undoable, like `pastePattern`: new track ids, empty steps, keeps the pattern's name and seed), `saveTemplate {index, name, overwrite?}` and `deleteTemplate {template}` (not undoable; they answer with a `templates` event; `init` lists the templates too). Confirmation is the UI's job, as for removing a track.
- Persistence: `Pattern::templateId` (32 bytes, ignored by the engine; undo, copy/paste and duplicate carry it) is saved as an optional `"template"` key; the schema stays v2 (older documents load, older builds ignore the key). The project keeps its tracks when a template is changed or deleted.
- Editor: a "Kit ▾" button in the bank bar (the bank's pattern name shrinks from 110 to 64 px and the transport text from 170 to 130 px, so the minimum width is unchanged) shows the pattern's template and opens a dropdown (`gui/TemplateList`, DGL-free, tested): "Built-in" and "My templates" sections by name, scrolling when they do not fit, × on user templates, and a last row that turns the dropdown into a name field to save the pattern's tracks. Loading into a pattern with active steps, overwriting or deleting a user template ask inside the dropdown (not the track-removal bar, which is tied to a track). Enter confirms, Esc steps back. Built and run only on Linux so far.
